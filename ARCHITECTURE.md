# FMail — Architecture

How the shipping app is built, and why. [`README.md`](README.md) covers what it does and how to
set it up; this file is the internals and the decisions behind them. Open work lives in
[`TODO.md`](TODO.md), completed items in [`DONE.md`](DONE.md).

> **History.** FMail began as a three-pane window app (sidebar / thread list / in-app HTML reader,
> plus Contacts-backed preferred-address handling). That UI was removed on `master` in commit
> `361dbbd`; the design-intent spec (`FMailSpec.md`), the window-era status doc (`IMPLEMENTATION.md`)
> and the MCP pre-implementation plan (`MCP_PLAN.md`) were retired with it and live in git history.
> The data layer they described — index, search DSL, threading, MCP — survived the UI change and is
> documented here in its current form.

---

## 1. Shape

Single Xcode app target, no packages, no third-party dependencies. Swift 6 language mode, SwiftUI +
AppKit, minimum macOS 14. The project file is generated by [xcodegen](https://github.com/yonaskolb/XcodeGen)
from `project.yml` and is not checked in.

The app runs as an `LSUIElement` accessory — a status-bar item, no window, no Dock icon. Everything
the user sees is an `NSMenu` built by `MenuBar/StatusItemController.swift`, except the Settings
window (`MenuBar/MinimalSettingsView.swift`, SwiftUI).

```
┌─────────────────────────────────────────────────────────────────┐
│  Presentation                                                   │
│  MenuBar/  — NSMenu: unread + search list, per-email submenu,   │
│              mark read/unread, MCP/Tunnel, Settings             │
│  MCP/     — JSON-RPC over HTTP for LLM clients (read-only)      │
│  Tunnel/  — cloudflared child process lifecycle                 │
└───────────────────────────┬─────────────────────────────────────┘
                            │
┌───────────────────────────┴─────────────────────────────────────┐
│  Core (pure Foundation + SQLite; no AppKit)                     │
│  Index/     — own SQLite + FTS5 mirror (schema v9)              │
│  QueryDSL/  — lexer → parser → AST → owner expansion →          │
│               evaluator → SQL + FTS5 MATCH                      │
│  Emlx/, HTML/, Threading/                                       │
└───────────────────────────┬─────────────────────────────────────┘
                            │ mirrors (read-only)
┌───────────────────────────┴─────────────────────────────────────┐
│  Sources                                                        │
│  ~/Library/Mail/V*/  — Envelope Index + .emlx + attachments     │
│  Mail.app via AppleScript — mark read/unread, reply/forward,    │
│                             refetch offloaded bodies            │
└─────────────────────────────────────────────────────────────────┘
```

**Key idea:** FMail never talks to mail servers. Apple Mail already syncs your accounts; FMail reads
its on-disk store, builds a better index on top, and presents a better list. Composing and reading
stay in Mail.app.

## 2. Data sources

### Apple Mail's local store

- `~/Library/Mail/V*/` — the version directory bumps with major macOS releases, so it's detected by
  listing `~/Library/Mail/V*` and taking the highest (`MailStore/MailboxURL.swift`).
- Per-account: `<UUID>/<Mailbox>.mbox/<UUID>/Data/Messages/*.emlx`.
- `MailData/Envelope Index` (SQLite) holds the metadata — `messages`, `addresses`, `recipients`,
  `subjects`, `mailboxes`, `labels`, `message_links`. Undocumented, and it *can* change between
  macOS versions (see §7).
- `.emlx` is RFC 822 plus a binary-plist trailer carrying the `read` / `flagged` / `replied` /
  `forwarded` bits. Parsed by a hand-rolled parser (`Core/Emlx/`): line folding, RFC 2047
  encoded-words, multipart MIME, base64, quoted-printable, RFC 2231 filename continuations.
- **Attachments are stored out-of-line for Gmail/IMAP accounts.** Mail.app strips the payload from
  the `.emlx` (leaving an `X-Apple-Content-Length` placeholder) and writes decoded bytes to
  `<dataDir>/Attachments/<rowid>/<partIdx>/<filename>`. `BodyLoader.fillExternalAttachments` pairs
  them back in after MIME parsing — by filename first, part-index order as fallback. Without that
  step every Gmail attachment parses as zero bytes.
- **"Optimise Mac Storage" offloads attachment bytes** while keeping the body on disk. So
  `body_on_disk: true` does not imply the attachment is local; the `attachments` table tracks
  `locally_available` per attachment, and `MailScripter.fetchBodies` can drive Mail.app to refetch.
- **Draft autosaves are excluded.** Apple's `messages.type = 5` marks Gmail draft autosaves;
  `EnvelopeIndexReader` filters them and `IndexDB.pruneMessagesNotIn` drops any that were imported
  before.

Access is strictly read-only — FMail never writes into `~/Library/Mail/`. Requires **Full Disk
Access**.

### Mail.app via AppleScript

`Compose/MailScripter.swift` shells out to `osascript` for the four things that must happen inside
Mail.app: mark read/unread (`setReadStatusBatch`), reply / reply all / forward
(`composeViaMailApp`), refetch an offloaded body or attachment (`fetchBodies`), and open a message
(`openMessage`, via the `message://` URL scheme). Requires **Automation** permission.

Batches are bucketed by mailbox and scoped per account where the account is known; a cross-account
fallback walks every mailbox matching on `apple_rowid`. Apple Mail's `id` is the Envelope Index
rowid, *not* the IMAP UID — the whole addressing scheme depends on that.

## 3. The index

`~/Library/Application Support/FMail/index.sqlite`, raw SQLite3 C API (no ORM), WAL enabled,
accessed through the `IndexDB` actor. Schema is versioned and migrated forward in
`Core/Index/Schema.swift` — **currently v9**.

Tables: `messages`, `recipients`, `threads`, `mailboxes`, `message_labels`, `message_links`,
`attachments`, plus the `messages_fts` virtual table.

```
messages_fts USING fts5(
    subject, body_clean, body_quoted, sender, recipients, attachment_names,
    tokenize = 'unicode61 remove_diacritics 2'
)
```

Column order is load-bearing: `bm25()` takes per-column weights positionally and `RelevanceTuning`
lists them in exactly this order.

Notable schema decisions:

- **Body text is split into `body_clean` / `body_quoted`** (v9) so quoted reply chains and
  signatures can be weighted near-zero at rank time instead of hijacking BM25.
- **`is_bulk`** (v9) flags newsletter / mailing-list mail at index time, from `List-Unsubscribe` or
  `Precedence: bulk|list|junk` (`Core/Emlx/BulkHeuristic.swift`).
- **`attachments`** (v8) carries `{name, content_type, byte_count, locally_available}` per
  attachment so `attachment-type:` / `attachment-size:` can filter without loading bodies.
- **Apple's `labels` table is mirrored** into `message_labels` — Gmail's INBOX / Sent Mail /
  Important are virtual label-mailboxes over `[Gmail]/All Mail`, so without this they index empty.
- `account_writeback` (v7) is vestigial: it belongs to the removed Gmail-writeback feature (§9) and
  is never read. The migration stays so version history remains linear.

### Sync

`UI/SyncCoordinator.swift` drives three paths:

1. **Full mirror** on first launch (and on schema-version bump).
2. **Incremental**, triggered by an `FSEventStream` rooted at the mail store
   (`kFSEventStreamCreateFlagFileEvents`, coalesced, persistent `lastEventId`), plus a **60 s
   periodic safety net** because FSEvents can miss things and a full sync is idempotent.
3. **Read-flag reconcile on menu open** (`syncReadFlagsNow`) — reads only the `read` bits from
   Apple's Envelope Index and updates changed rows, so marking something read in Mail.app shows up
   the next time the menu opens rather than at the next full sync.

`skipSyncsUntil` suppresses syncs for a short window after FMail itself drives an AppleScript write,
so Mail.app's own reflow doesn't race the optimistic update back.

`Core/Index/BodyIndexer.swift` runs a background sweep filling body text and attachment metadata
from `.emlx` files progressively; it pauses during a full sync (the connection is shared — see
`indexdb-reader-split` in TODO.md). Consequence, and it's user-visible: a brand-new message is
searchable by subject/sender/recipient/attachment-name immediately, by body slightly later.

### Threading

`Core/Threading/ThreadGrouper.swift` — union-find over `Message-ID` / `In-Reply-To` / `References`
as mirrored from Apple's `message_references`. Apple's own `conversation_id` is deliberately not
trusted.

## 4. Search

The pipeline is `Lexer → Parser → QueryNode (AST) → OwnerExpansion → Evaluator → CompiledQuery`,
and the same compiled query serves the menu list and the MCP `search_emails` tool. Grammar and
operators are documented for users in [README.md](README.md#search-syntax); what matters here is
the shape:

- **One boolean expression, not two.** Earlier versions routed text predicates through an FTS5
  expression and date/flag/scope predicates through a separate AND chain, so `(during:2025 OR
  during:2023)` silently became an AND and returned nothing. The evaluator now compiles the whole
  tree into one SQL boolean expression with FTS subqueries, while still fusing pure-text subtrees
  into a single `messages_fts MATCH` for speed.
- **Owner expansion is an AST→AST pass, not grammar.** `from:me` / `to:me` / `cc:me` / `in:sent`
  are rewritten against `IndexDB.ownerIdentities()` *after* parsing, because the parser has no index
  access — owner identities are data. With an empty owner set the rewrites degrade safely.
  `MCPSettings.nonOwnerAccounts` (a `defaults`-only array of account UUIDs or addresses) excludes a
  shared or family mailbox from that identity set. **The rewrite only runs in
  `MCPHandlers.searchEmails`** — the menu's own search path compiles the AST directly, so `from:me`
  is matched as a literal there. See `menu-owner-expansion` in TODO.md.
- **Address values are tokenised on non-alphanumerics.** FTS5 breaks email addresses at `@` and `.`,
  so `from:vendor.com` ANDs the tokens `vendor` and `com` against the sender column. A single-token
  search would miss every `@vendor.com` address.
- **Explicit AND between fused text branches.** FTS5's implicit-AND grammar rejects a parenthesised
  subexpression next to a column filter, so `(from:x OR to:x) subject:y` needs the explicit joiner.

### Relevance ranking

`sort: relevance` (MCP only — the menu list is always newest-first) blends four signals on top of
column-weighted BM25:

```
final = (bm25_normalized * bulkMultiplier)
      + lambda * exp(-age_days / tauDays)
      + proximityBoost * [row also matches NEAR()]
```

Defaults (`RelevanceTuning` in `Core/QueryDSL/Evaluator.swift`): subject 10, sender 8, body_clean 5,
recipients 2, attachment_names 2, body_quoted 0.3; `lambda` 0.2 over a 180-day decay;
`bulkMultiplier` 0.3; `proximityBoost` 0.15. BM25 is normalised to 0…1 against the top score in the
matched set first, so the additive terms live on a comparable scale. A relevance sort on a
metadata-only query falls back to newest-first.

`FMailTests/RelevanceEvalTests.swift` is an eval harness, not a unit test: it measures MRR and
nDCG@5 over 18 labelled queries in `relevance_fixtures.json` across four ranking stages (uniform →
weighted → +bulk discount → full), so a tuning change has to show it moved the metric.

## 5. Priority split

The unread list and every search result are split into **Priority** and **Other**
(`IndexDB.searchSplitByPriority`). A sender is priority when either:

1. **You've emailed them** — derived from your own sent mail (`IndexDB+Priority.swift`). Automatic,
   non-removable.
2. **They match a supplemental entry** — exact address, bare word / domain substring, or a `*`/`?`
   wildcard pattern, stored in `MenuBar/PriorityListSettings.swift` (UserDefaults).

Both the Settings pane and the per-message submenu can edit the supplemental list; the submenu shows
the matching entries verbatim, so a wildcard reads "Remove `*vendor.com` from Priority Mail".

## 6. MCP server

`MCP/` — a hand-rolled JSON-RPC 2.0 + minimal HTTP/1.1 framing on `Network.framework`'s `NWListener`
(no SDK dependency), listening on `127.0.0.1:8765`. **On by default**; an explicit toggle-off
persists. Twelve tools, all read-only against the index, plus the `fmail://schema` resource (and its
`describe_schema` tool mirror) that reports the live operators and filterable values in *this* index
so a client can ground queries instead of guessing.

Security posture, in order of how much it matters:

- **Read-only by design.** Mail state changes go through Mail.app. The one deliberate exception is
  `fetch_from_server`, which drives AppleScript to pull an offloaded body back from the server — it
  changes nothing in the mailbox. Enforced by convention today, not by the type system; see
  `mcp-readonly-seam` in TODO.md.
- **Attachment writes are confined.** Attachment bytes are attacker-controlled (anyone can email you
  a file) and FMail isn't sandboxed, so every `save_to_path` / `save_dir` from a *tunnel* connection
  must resolve inside `iCloud Drive/FMail`. Local connections are unrestricted. The root is in
  iCloud Drive deliberately: a save requested from the phone syncs back to the phone's Files app.
- **Auth.** Loopback with no token when no tunnel is configured; a static bearer token for local
  clients; OAuth 2.1 + PKCE session tokens for remote ones (`MCP/OAuth/`), issued only through a
  user-opened 5-minute approval window. If a tunnel is configured with neither a token nor a session,
  the server **fails closed**.
- **Host-aware OAuth discovery.** A loopback request is told the resource is
  `http://127.0.0.1:<port>/mcp`; a tunnel request gets the configured public URL. The bearer check is
  independent of the advertised issuer, so a local client's RFC 8707 resource check matches the URL
  it actually connected to.

`cloudflared` runs on your Mac, so tunnel traffic also arrives on `127.0.0.1` — the server cannot
distinguish a genuine local client from a remote one by address. That is why the token gates *all*
requests once a tunnel exists, and why the loopback-peer check is only defence in depth.

`Tunnel/TunnelCoordinator.swift` spawns `cloudflared tunnel run <name>` as a child process against a
temporary ingress config, parses stderr for the registration line, and tears it down on toggle-off
and on `applicationWillTerminate`. Tunnel state is deliberately **not** persisted across launches:
opening a public ingress to your mail is an active decision, and "I forgot the tunnel was open" is
the failure mode the menu checkmark exists to prevent.

## 7. Robustness against Apple changing things

`~/Library/Mail/V*/` and the Envelope Index schema are private API in spirit. Mitigations:

- Detect the store version dynamically rather than hardcoding `V10`.
- Treat the Envelope Index as a hint; `.emlx` files on disk are canonical content.
- Never write to Apple's files — all FMail state is in FMail's own database.
- Schema-version the local index and migrate forward; refuse to open a DB newer than the binary
  understands (`IndexDBError.schemaTooNew`).

A schema-fingerprint test against a live Envelope Index is still outstanding.

## 8. Testing

XCTest, 27 files. The load-bearing ones: query DSL parser/evaluator (including the FTS5
column-filter-AND regression), `IndexDB` dedupe / deletion / priority / thread-window behaviour
against real temp databases, `.emlx` and MIME parsing, `BodyLoader` external-attachment and RFC 2231
coverage against a synthetic Mail.app layout, MCP dispatcher / auth / HTTP framing / tool handlers
against an in-memory index, the OAuth flow, and the relevance eval harness.

One standing hazard: **no test may call `ReadStatusController.setReadStatus`.** `MailScripter`
runs `osascript` unconditionally, and a fixture rowid can collide with a real one in your actual
mailbox — the cross-account fallback would then mutate genuine mail. Enforced today only by a doc
comment; see `mailscripter-test-guard` in TODO.md.

## 9. Decisions, and things deliberately not built

| Decision | Outcome |
|---|---|
| GRDB vs raw SQLite3 C API | **Raw.** Zero dependencies; verbose but the schema is small. |
| Sandboxed? | **No.** FSEventStream interaction unproven, and the tunnel spawns a subprocess. Ad-hoc signed, not notarised. |
| `.emlx` parsing | **Hand-rolled.** No public Apple API exists. |
| Compose | **Mail.app's own AppleScript commands**, so replies quote correctly. An earlier `mailto:` path lost the quoted body and let Mail pick the From account by heuristic. |
| Body rendering | **Not done at all.** "Open in Mail" hands off — Mail.app is faster and more reliable at fetching and displaying a message than re-rendering it would be. |
| Search interface for MCP | **One DSL string**, not a second structured-params tool. The grammar ships in the tool description. |
| Default search scope | Drafts, trash and junk are excluded unless you scope to them with `in:` — by canonical mailbox kind *and* by Gmail label, since Gmail's folders are flat. |
| Telemetry | None. |

Removed after shipping, and not coming back without a new reason:

- **Contacts / preferred-address handling** (`contact_prefs`, the reply-confirmation address picker).
  It solved a compose-time problem, and compose now happens in Mail.app.
- **In-app thread reader and WKWebView HTML rendering.** Removed with the window UI.
- **Gmail writeback + OAuth.** A PKCE OAuth flow and a Gmail-API/IMAP writeback router were built to
  work around macOS Tahoe breaking `junk mailbox of <account>` AppleScript resolution. It worked, but
  per-fork OAuth client registration, Keychain storage and refresh-token lifecycle were not worth one
  button. Move-to-Junk is simply not a feature.
- **MCP write tools** (`mark_read`, `delete_messages`, `move_to_junk`, `diagnose_junk_mailboxes`).
  Dropped so the connector is safe to expose over a tunnel: worst case, someone past the bearer token
  can read mail, not mutate it.

Deferred, designed-for but not started:

- **iOS companion.** iOS sandboxes Mail's data, so the Mac trick doesn't transfer. The intended shape
  is the Mac as indexer and iOS as reader: sync `index.sqlite` to iCloud Drive via `NSFileCoordinator`
  and open it read-only, reusing the DSL, threading and schema through a shared Swift package.
  CloudKit (bidirectional) is the upgrade path only if read-only on iOS proves too limiting.
- **Standalone daemon.** The MCP server dies with the app. Pivoting would mean extracting a
  `FMailCore` package behind a LaunchAgent — only worth it if "FMail must be running" actually bites.
